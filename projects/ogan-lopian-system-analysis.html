Ogan Lopian: requirements and testing for a public service app

One year as a System Analyst intern. I turned what Diskominfo Purwakarta needed into documents developers could build from, modeled the system, and tested two systems before handover.

System Analyst intern

The question

What does the Ogan Lopian app need to do for Purwakarta's residents, and how do we prove it works before launch?

Background

Ogan Lopian is a public service app for Purwakarta Regency, built by PT. Pratama Solusi Teknologi for Diskominfo Purwakarta. The same team also built a CSR management system. My job sat between the client and the developers: understand the need, write it down so nobody has to guess, and check the result against it.

Method

  1. Gathered requirements with Diskominfo Purwakarta and wrote them up as a BRD and a PRD.
  2. Translated the business needs into an SRS with use cases the developers could build from.
  3. Modeled the system with 20 UML diagrams, plus ERDs and flowcharts.
  4. Ran User Acceptance Testing for two systems and documented the bugs found.
  5. Summarised the work in a System Analysis Report, and supported the team with data and development tasks.

Result

  • Four core documents. BRD, SRS, PRD and a System Analysis Report for the Ogan Lopian app.
  • 20 UML diagrams. Plus ERDs and flowcharts that the developers built from.
  • Two systems through UAT. Acceptance tests run and bugs documented before handover.
  • 90% accuracy. A Random Forest model for social assistance eligibility, placed inside a dashboard.
  • Five authentication features. Built in Node.js, alongside a sentiment analysis of Google Play reviews.

What I took from it

  • Write acceptance criteria while gathering requirements, so UAT has something concrete to test against.
  • Use one diagram per question. A use case answers who does what, an ERD answers what is stored.
  • Keep the client and the developers reading the same document, so changes are caught early.
